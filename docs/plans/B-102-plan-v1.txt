  3.2 docs/QUESTION_FORMAT.md (the spec)

  Sections:

  1. Where things live:
     - questions/RPR-NNNN.md
     - figures/fig-NN.png and figures/index.json
     - data/references.json
     - data/acs-10b-knowledge.json
  2. IDs:
     - Format is RPR- plus 4 digits, matching the file name.
     - A new ID is the highest existing ID + 1. IDs are never reused and carry
       no meaning.
     - Question files are never deleted. An abandoned question is retired
       instead. Deleting the highest file would otherwise let the "+1" rule
       reuse its ID.
     - Run git pull before every q-writer batch, so the two machines can't
       collide on IDs.
  3. File layout:
     - Line 1 is ---, then YAML front matter, then ---.
     - The stem follows as plain paragraphs, then a line exactly ## Explanation,
       then the explanation.
     - Front matter keys appear in this fixed order: id, acs_code, figure,
       options, answer, sources, review. No other keys are allowed; in
       particular there is no area key, because the area is derived from the
       code.
     - review must be the last key, in block style (not {…}), with children
       indented.
     - No YAML comments and no HTML comments. This keeps drafting notes out of
       files under D-004.
  4. Field reference:
     - acs_code: must be in data/acs-10b-knowledge.json. The area is the Roman
       numeral in the code.
     - figure: null or a positive integer that is in figures/index.json.
     - options: a mapping with exactly the keys A, B, C (my reading of decision
       2; see Open question 9). Each value is a non-empty, double-quoted string,
       and the three must differ ignoring case and whitespace.
     - answer: one of A, B, C.
     - sources: a list with at least one entry. Each entry has doc, edition
       (copied exactly from the index), location, and passage. All are non-empty
       strings.
     - Area I questions need at least one cfr-107 source.
  5. Body rules:
     - The stem is non-empty, with no headings, no HTML (< followed by a letter
       or /), and no images (![).
     - The explanation has the same restrictions.
     - Both follow the public-text writing rules.
     - A "passage" means the words as printed. Line-break hyphenation and
       whitespace are normalized, and characters like § are used as printed.
  6. Review block and status lifecycle: a who-sets-what table based on
     decision 7. Recommended transitions to confirm are in Open question 5.
     - For a new question, q-writer writes status: draft and sets the other four
       review fields to null.
     - approved requires reviewed_by, reviewed_at ("YYYY-MM-DD", quoted), and a
       matching content_hash.
     - returned and held require reviewed_by, reviewed_at, and non-empty notes.
     - draft, returned and held must have content_hash: null.
  7. content_hash algorithm, step by step (also see Open question 8):
     a. The file must be UTF-8 with no BOM.
     b. Convert CRLF and lone CR to LF.
     c. Remove the line review: and every line after it up to, but not
        including, the closing ---.
     d. Strip trailing spaces and tabs from every line.
     e. Remove trailing empty lines and end with exactly one LF.
     f. Take the SHA-256 and write it as lowercase hex.
     - It's computed with npm run qbank:hash -- questions/RPR-NNNN.md. Because
       the review block is excluded, a status change never changes the hash.
  8. Loader contract, for the future loader plan:
     - It loads approved and retired questions only.
     - It refuses any approved question whose hash doesn't match.
     - Retired questions are never drawn into new exams.
     - The pending points are in Open questions 5, 6 and 10.
  9. The validator: how to run it, and the list of checks with their IDs (from
     3.6).

  3.4 data/acs-10b-knowledge.json and how it's extracted

  { "doc": "acs-10b", "source_sha256": "9ee24463…", "extracted_with": "pdftotext
  -raw (Xpdf 4.00)",
    "areas": [ { "numeral": "I", "title": "Regulations" }, … ],
    "elements": [ { "code": "UA.I.B.K10", "area": "I", "task": "B",
  "description": "Visual line of sight (VLOS) aircraft operations." }, … ] }

  scripts/qbank/extract-acs.ts:
  1. Checks the PDF's SHA-256 against references.json for acs-10b and stops if
     it doesn't match.
  2. Runs pdftotext from $PDFTOTEXT, then PATH, then the Git for Windows path,
     always with -raw and never -layout.
  3. Element lines match ^(UA\.(I|II|III|IV|V)\.([A-Z])\.K\d+[a-z]?)\s+(\S.*)$.
     A description continues onto the following lines until the next code line
     or a line that starts with Risk Management, Skills, References, Objective,
     Task , or an area heading. Page-number-only lines are skipped.
  4. Areas come from the Appendix 1 lines ^(I|II|III|IV|V)\. (.+?) \d+-\d+%$.
  5. Writes the JSON with 2-space indent and LF line endings. --check
     re-extracts and compares with the committed file, ignoring line-ending
     differences.
  6. Asserts exactly 176 unique codes, per-area counts I=77, II=26, III=17,
     IV=4, V=52, five areas, and no empty description. These are hardcoded
     literals, never read from the file under test.

  - the codes are unique, match the regex, and number 176

  * text=auto eol=lf
  *.png binary
  *.jpg binary
  *.ico binary
  *.pdf binary

  4. Risks

  - Changing an approved question would rewrite history. Each attempt stores
    option order as A/B/C keys (D-021), and the review shows the question and
    its media (D-020). If approved text changes in place, old reviews show
    content the user never saw, and old scores may no longer fit the key. The
    format should treat approved content as immutable (Open question 5).
  - A loader that drops held questions would break past reviews. If an approved
    question later becomes held and the loader simply stops loading it, past
    attempts lose their question. The loader must never delete rows; it should
    only mark them as not drawable (Open question 5).
  - Removing the review block by text depends on format rules. The validator
    enforces those rules (review last, block style). A file that breaks them
    fails validation instead of being hashed wrongly.
  - pdftotext versions differ. Another build (for example Poppler) may produce
    different raw text, so --check can fail because of the tool rather than the
    PDF. extracted_with records the version used.
  - B-115 scaffolding has to merge into this root package.json and must not
    overwrite it.
  - YAML typing: unquoted 400 parses as a number. The schema check catches it,
    and the agents are told to quote strings.
  - Area derivation feeds readiness (D-003) and exam weighting (D-032/033). The
    future app must take area numerals and titles from the ACS data file rather
    than hardcoding them.
